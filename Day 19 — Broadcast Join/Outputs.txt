[info] 17. WHEN IS BROADCAST JOIN APPROPRIATE?
[info] ==========================================================================================
[info] Use broadcast join when:
[info] 1. One side of the join is small.
[info] 2. The small dataset can comfortably fit in the
[info]    memory available to executors.
[info] 3. The large dataset should avoid a full shuffle.
[info] 4. The small dataset is reused across many records
[info]    of the large dataset.
[info] Examples:
[info] Transaction Fact + Branch Master
[info] Sales Fact + Product Master
[info] Orders + Small Customer Reference
[info] Events + Country/Region Lookup
[info] Employees + Department Master
[info] ==========================================================================================
[info] 18. WHEN SHOULD YOU AVOID BROADCAST JOIN?
[info] ==========================================================================================
[info] Avoid broadcast when:
[info] 1. The supposedly small table is actually very large.
[info] 2. Broadcasting it would consume excessive executor memory.
[info] 3. The reference table cannot comfortably fit on
[info]    the executors.
[info] 4. The dataset size changes significantly and may
[info]    become too large to broadcast.
[info] Potential problem:
[info] Large table
[info]       +
[info] Broadcast large table
[info]       |
[info]       v
[info] Executor memory pressure
[info]       |
[info]       v
[info] Possible performance degradation or failure

[info] 22. DAY 19 VIVA SUMMARY
[info] ==========================================================================================
[info] Q1. What is a broadcast join?
[info] A:
[info] A broadcast join distributes a small dataset to the
[info] executors so it can be joined locally with a larger
[info] dataset without shuffling the large dataset.
[info] Q2. Why is broadcast join useful?
[info] A:
[info] It can avoid a large shuffle when one side of the
[info] join is sufficiently small.
[info] Q3. What function explicitly requests broadcasting?
[info] A:
[info] broadcast()
[info] Example:
[info] transactions.join(
[info]     broadcast(branches),
[info]     ...
[info] )
[info] Q4. What should be small for a broadcast join?
[info] A:
[info] The side being broadcast should be small enough to fit
[info] comfortably in executor memory.
[info] Q5. What is Shuffle Sort Merge Join?
[info] A:
[info] It is a join strategy where data is shuffled according
[info] to the join key, sorted within partitions and then merged.
[info] Q6. What is the major difference?
[info] A:
[info] Broadcast Join:
[info] Small side is broadcast to executors.
[info] Shuffle Sort Merge Join:
[info] Both sides are generally repartitioned/shuffled and sorted.
[info] Q7. Why can shuffle be expensive?
[info] A:
[info] It may require network transfer, serialization,
[info] disk I/O and sorting.
[info] Q8. Does row count alone determine whether a table
[info] should be broadcast?
[info] A:
[info] No. The actual size of the serialized dataset and
[info] available executor memory matter.
[info] Q9. What happens if we broadcast a very large table?
[info] A:
[info] It can create substantial memory pressure on executors
[info] and can hurt performance or cause failures.
[info] Q10. What is the banking use case in this project?
[info] A:
[info] Millions of transactions are joined with a small branch
[info] master using branch_id. The branch master can be broadcast
[info] to enrich every transaction with branch information.
